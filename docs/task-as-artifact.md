# 任务即制品：PACT 中的任务记录与任务状态

对应规范：`paper/pactv1_rev3.md`（下称“母本”）§1.2、§1.3、§1.4、§1.5、§2.1、§4.1–§4.3，附录 B。
本文件回答一个具体问题：**把 `ThingRef` 指向任务而不是文件，PACT 还能不能完成流程编排与 agent 协调？**

结论先行：

- **能表达**：把任务记录放进 `ThingRef`、把任务状态或位置放进 `TypeName`，今天就能写，不改语法、不改语义。
- **得到的是“受治理的任务板”**，不是“任务图执行器”。拓扑可以等价，执行语义不等价。
- 本文只讨论这两种当前可写的用法。需要改范式的部分（恰好一次、同任务配对、动态任务等）只作为**缺口或范式边界**登记，不讨论扩展方案。

阅读顺序：§2 节点是什么 → §3 两种用法 → §4 与图编排对比 → §5 与 agent 协调对比 → §6 能力边界 → §7 用法约束。

---

## 1. 先分清两件事

| 问题 | 属于 | 改变它需要 |
|---|---|---|
| `ThingRef` 指向文件、任务还是别的什么 | **内容问题** | 什么都不用改；运行时传不同的引用即可 |
| 任务能不能按实例被匹配、能不能保证一次派发 | **匹配粒度问题** | 改规则、改匹配键，属于范式扩展候选 |

“物引指向任务”只落在第一行。它不会自动把 PACT 变成任务图执行器；第二行才是关键。

## 2. 节点是类型，不是物引

### 2.1 token 的三段结构

母本 §3.2 的 token 是：

```text
Token ::= { TokenId, TypeName, ThingRef, ParticipantName, PrecondRefs, Timestamp }
```

| 段 | 承载物 | 回答什么 |
|---|---|---|
| 位置 / 条件 | `TypeName` | 它在流程的哪一格、表示哪种事实 |
| 实例身份与生命周期 | `TokenId` + `Counter` / `Archive` | 具体是哪一枚、现在还在不在 |
| 内容 | `ThingRef` | 指向外部什么东西 |

严格说，图上的节点既不是 token，也不是物引，而是 `TypeName`。token 是节点上的一个实例/标记：同一类型可以同时有多枚 token（多实例、多读者）；CPN 里对应的就是同一个 place 上的多个 marking。

`ThingRef` 对范式是**不透明的**：母本 §1.3 明确不定义它的相等、版本、可变性与基数；两个 token 可以引用同一个外部对象，一个外部对象也可以被多个 token 引用。母本 §4.4 也明确，Rule-P 与 GateExpr 不读 `ThingRef`。

### 2.2 在 CPN 编码里，节点是位所

母本附录 B 的构造是：**每个 `TypeName` 建一个 place**（附录 B.2），**每个 `(participant, produces T)` 建一个 transition**（附录 B.3）。所以：

- PACT 的“节点”是**位所 / 条件**，不是动作；
- 动作（生产、读取、消费）是**迁移**，由参与者显式发起；
- `ThingRef` 在 place 内部，是 token 的内容。

这与主流图式编排正好相反：图编排的节点通常是**任务 / 动作**，边是控制流。把 `ThingRef` 指向任务，只是让某枚 token 里装的是一张任务卡；**任务卡不会把 place 变成 transition**。

### 2.3 一个必须满足的语义约束

Rule-P 的前提是前驱 token **仍在 Counter 上**（§1.4）。所以 `A → B` 意味着：

> 生产 B 时，A 所表示的事实必须已经成立。

因此，类型 A 必须表示**任务的后置事实或当前状态**（完成、就绪、已批准、产出已存在），**不能表示“任务 A 待办”**。否则 B 会在 A 还没完成时就被使能，流程语义直接坏掉。

这条约束是下文所有用法的前提，也是“任务即制品”这个说法里“制品”二字的真正含义：**不是“任务这个动作”，而是“任务的状态/结果这个可数事实”**。

## 3. 两种当前可写的用法

### 3.1 用法一：任务记录作为物引

`.pact` 文件里不写物引值；它在 `seed` / `produce` 时通过 `--thing-ref` 传入：

```bash
pact seed    --domain task_board --participant planner --type task_open --thing-ref 'task://BOARD-42'
pact produce --domain task_board --participant planner --type task_doing \
             --predecessors <task_open-id> --thing-ref 'task://BOARD-42'
```

**得到：**

- 任务内容外置，PACT 不解释它；
- 同一类型可以承载不同任务实例，实例由 `TokenId` 区分；
- 审计可以按 token / 物引追溯；
- 参与者可以读取物引**自行**做路由、去重、幂等。

**不得到：**

- gate 不能按物引做准入（§1.3、§4.4）——引擎不知道 `task://BOARD-42` 和 `task://BOARD-43` 有什么区别；
- 不能表达“同一个任务的两次动作必须配对”；
- 不定义物引的版本、基数与唯一性。

**适合：** 外部已有任务系统（Jira、工单、看板），PACT 只治理任务状态的准入；agent 自己按物引识别“这是我的任务”。

### 3.2 用法二：任务状态或位置作为类型

任务在流程中的位置必须写进 `TypeName`。同一个任务图有三种等价写法，区别只在 token 表示哪一种事实：

| 写法 | 例子 | token 表示 |
|---|---|---|
| 完成态 | `build_done` | “build 已经完成” |
| 就绪态 | `build_ready` | “build 可以被领取” |
| 产出态 | `build_artifact` | “build 的产出已经存在” |

三者可以在域声明里转换，选哪种取决于你想让 gate 和下游看到什么事实。**不要**写成 `build_task`（待办），那会违反 §2.3 的约束。

**得到：**

- 任务 DAG 的拓扑：母本 §4.1 的构造编码正是把活动 `Aᵢ` 映射为 `output-of-Aᵢ`，把 `(Aᵢ, Aⱼ)` 映射为 `Tᵢ → Tⱼ`；它覆盖 SOAD（单输出、AND 结构）工作流；
- 每个位置独立的 gate：谁可以读、谁可以生产下一格、谁可以消费；
- 六项静态分析（附录 A / D）：前置良构、可达性、生产覆盖、消费可达、结构死锁、搁浅风险；
- 原生的审计与溯源：`depends_on` 记录直接前驱，`via` 可以要求“生产时用的那枚前驱”现在仍在场（§1.4.0）；
- 多读者：同一枚 token 可以被多个只读参与者同时观察（Part II §4.1）。

**不得到：**

- 同一任务多实例的配对（见 §6）；
- 恰好一次执行（见 §6）；
- 动态任务 / 动态 schema（B16、B19）；
- 自动推进、超时、重试（B2、B6）。

**代价：** 类型数按“任务位置 × 状态”增长；任务种类必须有限且静态声明。

### 3.3 两者组合：位置进类型，实例进物引

这是“任务即制品”的规范写法：

| 任务维度 | 放在哪里 |
|---|---|
| 任务在流程中的位置 / 当前状态 | `TypeName` |
| 具体是哪个任务实例 | `TokenId`（以及 `ThingRef` 里的外部任务 id） |
| 任务的正文、附件、外部系统记录 | `ThingRef` |

一句话：**范式管位置，物引管身份，参与者管内容。**

可运行示例见 [`examples/task-as-artifact/`](../examples/task-as-artifact/README.md)：`task_board.pact` 演示“状态作为类型 + 任务 id 作为物引”，`task_dag.pact` 演示“任务产出作为类型”的 §4.1 编码。

## 4. 与基于图的流程编排对比

对照对象：LangGraph 这类图式 agent 编排、Airflow / n8n 这类 DAG 调度、BPMN 流程引擎。它们的具体能力不同，但共同点是**节点是任务 / 动作，边是控制流**。

| 维度 | 基于图的流程编排 | PACT（任务即制品） |
|---|---|---|
| 节点是什么 | 任务 / 动作 / agent 步骤 | 类型化的状态或后置事实（CPN 里是 place） |
| 边是什么 | 控制流，常带数据依赖 | 存在性前置：生产 B 时 A 必须在场（Rule-P） |
| 运行时对象 | 图 + 调度器状态 | 单一 Counter + Gate 矩阵 |
| 谁决定下一步 | 调度器 / 图执行器 | 参与者：Rule-W 自驱，没有中心派发 |
| 推进方式 | 自动、级联、可重试 | 显式动作；零隐式动作（§1.4 设计原则） |
| 同一任务只执行一次 | 通常由引擎保证 | **不保证**：Rule-P 不消费前驱，消费是另一个显式动作 |
| 多实例 join | 运行时按实例配对 | 类型级 AND；同任务多实例配对不在范式内（B14、B20） |
| 失败 / 重试 / 超时 | 引擎原语 | 范式外：无时钟、无自动生命周期（B2、B6） |
| 动态加任务 / 改图 | 支持 | 静态类型（B16、B19） |
| 审计 | 日志，通常需额外关联 | `Archive` + `depends_on` + `via` 原生 |
| 静态分析 | 有限，取决于图与代码 | 声明级六项分析（附录 A / D） |

三个关键差异：

1. **节点语义不同。** 图节点是“做什么”；PACT 节点是“什么已经存在”。这决定了 PACT 天然是准入模型，不是执行模型（§1.3 末句：*admission, not compulsion*）。
2. **调度器状态放在哪里。** 图编排把状态藏在引擎里；PACT 把它外化成公共、可审计的 token，并把“是否推进”的决定分散给参与者。
3. **图是不是运行时对象。** 图编排的图就是运行时；PACT 的图是导出的第二表示（`pact cpn`），真相源是域声明与 Counter。

因此：

- **拓扑可以等价**（在 §4.1 的 SOAD 范围内）；
- **执行语义不等价**：图引擎的自动点火、恰好一次、重试、超时、原子多输出，PACT 不承诺。母本 §4.3 已明确，原子多输出是 Petri 网有而 PACT 没有的行为。

## 5. 与 agent 协调对比

图式 agent 编排与 agent 框架（CrewAI、AutoGen、OpenAI Agents SDK 等）通常围绕“派活”组织：谁把哪个任务交给哪个 agent、消息怎么传、会话怎么交接。PACT 不建队、不派活、不传消息（手册 §1.2）。

| 问题 | 图式 agent 编排 / agent 框架 | PACT 任务即制品 |
|---|---|---|
| agent 怎么知道下一步做什么 | 调度器推送 / 图边转移 | 读 Counter，看自己的 gate 与前置是否满足（Rule-W） |
| 任务怎么分配 | 中心派发或显式 handoff | 没有派发；多个 agent 可同时看到同一枚“就绪”token（多读者） |
| 跨 harness 协调 | 通常需要共享运行时或消息总线 | 单一 Counter 作为共享准入权威，不需要 agent 直接通信（Part III Ch.2） |
| 溯源 | 依赖日志与追踪系统 | `depends_on` / `via` 是 token 语义的一部分 |
| 执行保证 | 框架/引擎承担 | 不承担；执行、重试、超时在参与者或外部系统 |

**适合 PACT 的 agent 场景：**

- agent 是自治的，不需要被逐个派活；
- 多个 agent / harness 通过共享任务状态协作，而不是通过消息；
- 需要“谁能动哪个任务、动之前要看到什么”可审计；
- 任务本来就存在于外部系统，PACT 只治理状态。

**不适合 PACT 的 agent 场景：**

- 需要严格按图执行、每步只跑一次、失败自动重试；
- 需要中心化调度、超时、补偿事务；
- 任务图在运行时动态生成、节点无界。

## 6. 能力边界：为什么它不是一个任务图执行器

以下都是**缺口登记**，不是扩展方案。需要这些保证时，应选择图执行器 / BPMN / 持久化执行引擎，或在 PACT 外再包一层执行器。

| 缺口 | 母本依据 | 后果 |
|---|---|---|
| **恰好一次** | §1.4 Rule-P（前驱不消费）+ Rule-E（消费是独立动作） | 生产不保证“恰好一次”：同一前驱可以支撑多次生产，两个生产者能对同一前驱各产一枚 `done`；消费与生产也是两个动作，不是一次原子提交。范式不提供去重保证 |
| **同一任务多实例配对** | §1.4.0（`via` 只看直接前驱）、§1.4.4（类型级 AND） | `{ result + approval } → done` 只保证两枚 token 在场，不保证它们来自同一个任务；无祖先查询（B14、B20） |
| **动态任务 / 动态 schema** | §2.2、§3.1（四个注入点静态） | 任务种类必须预先声明；无界任务无法在声明中表达（B16、B19） |
| **超时 / 租约到期 / 重试** | §1.3（`Timestamp` 无语义）、§1.6 | 范式不比较时间戳、不自动重试；这些保证不在范式内（B2、B6） |
| **OR 分支** | §1.4.4 RHS Uniqueness | 不能把两条分支汇聚到同一后继类型（B4、X1） |
| **原子多输出** | §4.3 | 一次 Rule-P 只产一枚 token；多输出会暴露中间态（B15、X3） |
| **任务正文 / 字段级约束** | §1.3、§2.3 | 任务内容在 `ThingRef` 里，范式不解释，不能做字段级 gate（B5） |
| **按任务身份路由** | §1.3、§4.4（`ThingRef` opaque） | 让 gate 读 `ThingRef` 会滑向无界内容寻址（X4）；有限分类必须编进 `TypeName` |

结论：

> **PACT 能表达“任务板”及其准入规则，不能表达“任务图执行器”的执行保证。**  
> 物引指向任务是合法的；它换不来恰好一次、自动推进、同任务配对或动态任务。

## 7. 用法约束（不构成对 §6 缺口的解决方案）

1. **位置进类型，实例进物引。** 任务在流程中的哪一格用 `TypeName` 表示；具体是哪个任务用 `TokenId` + `ThingRef` 表示。
2. **类型级 AND 不区分实例。** 同一类型上并发停留多个任务时，下游 AND 只保证“各有一枚”，不保证来自同一个任务；这正是 §6 的缺口，不是配置能关掉的开关。
3. **需要按任务路由时，参与者可以读 `ThingRef` 自己判断。** 引擎与 gate 不会替你做；但不要因此让 gate 读物引（X4）。
4. **用 `via` 保直接前驱，用多读者做广播。** `via` 只保证“生产时用的那枚直接前驱”现在还在，不保证“先后顺序”；顺序要靠消费策略（见 [`token-consumption-timing.md`](token-consumption-timing.md)）。
5. **把执行保证放到参与者或外部执行器。** 需要恰好一次、重试、超时、动态任务时，PACT 只做准入与审计，执行交给外部。
